## Risultato

Nuovo modulo puro `src/world/chunk/persistent.ts`: contratto
`PersistentChunkStore` (`get/put/delete/clear/quota`) con errori tipizzati e
implementazione in-memory per i test. La chiave persistente riusa il namespace
della warm cache senza ricalcolarlo; `persistentKeyFrom` lo riceve come stringa
e lo propaga identico.

Comportamento osservabile:
- `get` su store vuoto non lancia: restituisce un miss tipizzato
  (`{ status: "miss", reason: "absent" }`); con storage assente
  (`{ status: "miss", reason: "unavailable" }`).
- `put`/`get` fanno roundtrip di byte con copia difensiva in scrittura e in
  lettura: mutare l'array del chiamante o quello letto non altera l'entry.
- Budget dichiarato alla costruzione: `put` evince l'entry meno recente per
  rientrare nel budget; se un singolo payload supera il budget lancia
  `quota-exceeded` **prima** di qualsiasi eviction, quindi i dati gia' scritti
  restano leggibili.
- Storage assente: `get` -> miss `unavailable`, `put` -> `storage-unavailable`,
  `delete` -> `false`, `clear` -> resolve, `quota` -> zeri. La sessione non
  richiede lo storage per procedere.

Limiti ancora presenti: nessuna serializzazione/validazione del payload
(CACHE-03) e nessun backend reale (CACHE-02); l'implementazione e' in-memory e
perde i dati alla chiusura, per progetto.

### Firme API finali

```ts
type PersistentStoreErrorCode =
  | "invalid-key" | "invalid-value" | "quota-exceeded"
  | "storage-unavailable" | "store-failure";

class PersistentStoreError extends Error {
  readonly code: PersistentStoreErrorCode;
  constructor(code: PersistentStoreErrorCode, message: string, cause?: unknown);
}

interface PersistentChunkKey {
  readonly namespace: string;        // namespace warm cache, riusato verbatim
  readonly chunkId: string;
  readonly compilerVersion: string;
  readonly schemaVersion: number;    // schema del chunk compilato
}

function assertPersistentChunkKey(key: PersistentChunkKey): PersistentChunkKey;
function persistentKeyFrom(cacheKey: ChunkCacheKey, schemaVersion: number): PersistentChunkKey;

type PersistentReadResult =
  | { readonly status: "hit"; readonly value: Uint8Array }
  | { readonly status: "miss"; readonly reason: "absent" | "unavailable" };

interface PersistentQuota { readonly budgetBytes: number; readonly usedBytes: number; readonly entries: number; }

interface PersistentChunkStore {
  get(key: PersistentChunkKey): Promise<PersistentReadResult>;
  put(key: PersistentChunkKey, value: Uint8Array): Promise<void>;
  delete(key: PersistentChunkKey): Promise<boolean>;
  clear(): Promise<void>;
  quota(): Promise<PersistentQuota>;
}

interface MemoryChunkStoreOptions { readonly budgetBytes: number; readonly available?: boolean; }
function createMemoryChunkStore(options: MemoryChunkStoreOptions): PersistentChunkStore;
```

Errori e confini rilevanti per i task successivi:
- `invalid-key`: namespace/chunkId/compilerVersion vuoti o > 512 caratteri,
  `schemaVersion` non intero non negativo, marker di credenziale
  (`token`, `secret`, `password`, `authorization`, `bearer`, `api_key`, ...),
  oppure namespace costruito su identita' opaca per istanza `["instance", n]`.
- `invalid-value`: payload non `Uint8Array` o vuoto.
- `quota-exceeded`: il payload non entra nel budget dichiarato; nessuna entry
  preesistente viene rimossa.
- `storage-unavailable`: storage assente/negato (il chiamante prosegue).
- `store-failure`: riservato ai backend (CACHE-02), non prodotto dall'in-memory.
- Budget non valido in costruzione: `Error` semplice, come `createChunkCache`
  in `cache.ts` (errore di configurazione, non di storage).
- Ownership: `put` copia il payload, `get` restituisce una copia; il chiamante
  non condivide buffer con lo store.
