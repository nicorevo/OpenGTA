## Risultato

Nuovo backend persistente `IndexedDbChunkStore` in
`src/world/chunk/persistent-indexeddb.ts`, dietro il contratto
`PersistentChunkStore` di CACHE-01 (nessuna modifica al contratto). Database
versionato (`opengta-persistent-chunks` v1) con un object store
`chunk-entries` senza keyPath: la chiave primaria e' lo stesso id del backend
in-memory (`JSON.stringify([namespace, chunkId, compilerVersion, schemaVersion])`),
quindi le due implementazioni sono intercambiabili entry per entry. Il payload
e' memorizzato come `Uint8Array` (put riceve gia' bytes; la serializzazione del
chunk compilato resta a CACHE-03) con copia difensiva in scrittura e in lettura:
il chiamante non condivide mai buffer con lo store.

Comportamento osservabile:
- `get` non lancia mai per storage assente/negato/rotto: restituisce un miss
  tipizzato (`absent` se l'entry non c'e', `unavailable` se lo storage non e'
  utilizzabile). Un record corrotto o di forma ignota e' un miss `absent`, non
  un hit e non un'eccezione.
- `put` degrada con `PersistentStoreError("storage-unavailable")` quando la
  factory `indexedDB` manca, e' negata, l'open e' bloccato da un'altra
  connessione, il DB e' piu' nuovo del client o la connessione e' stata
  invalidata; qualsiasi altro guasto del backend e' `store-failure`; un
  `QuotaExceededError` del browser o un payload oltre il budget dichiarato sono
  `quota-exceeded`. Un put rifiutato non rimuove entry gia' memorizzate.
- `delete` -> `false` senza storage; `clear` e' best effort e risolve sempre;
  `quota` senza storage riporta zeri (stessa forma dell'in-memory).
- Budget dichiarato alla costruzione (default 32 MiB) con eviction delle entry
  scritte meno di recente; la prima scrittura di una sessione riconcilia una
  volta con l'indice persistito, poi l'accounting e' O(1) e `quota()` resta la
  misura autorevole (scansione completa).
- Nessuna throw incontrollata: l'unico errore non tipizzato e' la configurazione
  invalida del budget in costruzione (`Error` semplice, come
  `createMemoryChunkStore`).

Limiti ancora presenti: nessuna validazione del contenuto del payload (CACHE-03)
e nessuna integrazione nella sessione (CACHE-04); le misure write/read/quota non
sono state eseguite (vedi AC2).

### Firme API finali

```ts
const PERSISTENT_DATABASE_NAME: string = "opengta-persistent-chunks";
const PERSISTENT_DATABASE_VERSION: number = 1;
const PERSISTENT_ENTRY_STORE: string = "chunk-entries";
const DEFAULT_PERSISTENT_BUDGET_BYTES: number = 32 * 1024 * 1024;

interface IndexedDbChunkStoreOptions { readonly budgetBytes?: number; }

interface IndexedDbChunkStore extends PersistentChunkStore {
  close(): Promise<void>;   // aggiunta additiva al contratto, non lo modifica
}

function createIndexedDbChunkStore(options: IndexedDbChunkStoreOptions = {}): IndexedDbChunkStore;
// get/put/delete/clear/quota sono esattamente quelli di PersistentChunkStore.
```

Errori e confini rilevanti per i task successivi:
- Codici prodotti: `invalid-key` e `invalid-value` (validazione locale, stessa
  forma e stesso ordine dell'in-memory: chiave, payload, disponibilita',
  budget), `storage-unavailable` (factory assente/negata, open bloccato o
  fallito, DB piu' nuovo del client, connessione invalidata), `quota-exceeded`
  (payload oltre il budget dichiarato, verificato **prima** di ogni eviction, e
  `QuotaExceededError` del browser), `store-failure` (ogni altro guasto del
  backend).
- Chiave primaria = id del backend in-memory: una entry scritta da CACHE-01 o
  da CACHE-04 in-memory e' leggibile identica da IndexedDB e viceversa.
- Ownership: `put` copia, `get` restituisce una copia.
- Budget: eviction per data di scrittura (una lettura non promuove l'entry),
  riconciliazione una tantum alla prima scrittura di sessione; questa scelta e'
  documentata nel modulo ed e' l'unico punto in cui il comportamento differisce
  dall'in-memory (che promuove in lettura).
- `close()` invalida la connessione e l'accounting: la successiva operazione
  riapre il database.

## Handoff

- CACHE-03 (validazione): `get` restituisce esattamente i byte scritti, come
  copia; un record di forma invalida e' gia' un miss `absent` e non arriva mai
  come hit. La validazione del contenuto del payload resta interamente a
  CACHE-03: `delete` + miss e' il percorso previsto per un'entry corrotta.
- CACHE-04 (integrazione): usare `persistentKeyFrom(cacheKey, schemaVersion)`
  con una `sourceIdentity` stabile (un namespace con `["instance", n]` viene
  rifiutato con `invalid-key`); il budget si dichiara in costruzione
  (`DEFAULT_PERSISTENT_BUDGET_BYTES` se non si vuole decidere ora). Senza
  storage o con quota piena la sessione non deve cambiare percorso: `get` ->
  miss `unavailable`, `put` -> `storage-unavailable`. `close()` e' disponibile
  per il teardown della sessione.
- Gate orchestratore: la spec E2E e' l'unico punto che misura su IndexedDB
  reale; i numeri vanno raccolti con l'ambiente dichiarato e usati per AC3.
- Debito tecnico residuo: l'accounting del budget e' per istanza di store (due
  store sulla stessa pagina condividono il DB ma non il contatore; il primo
  `put` di ciascuno riconcilia); la riconciliazione legge i payload con
  `getAll()` una volta per sessione, accettabile al budget dichiarato ma da
  rivedere se il budget cresce molto.

Scostamenti dalla scheda:
1. Eviction per data di scrittura invece che per recency di lettura: la lettura
   resta una singola richiesta IndexedDB, il che conta di piu' del
   raffinamento dell'ordine di sfratto. Documentato nel modulo.
2. Aggiunto `close()` come estensione additiva dell'interfaccia; il contratto
   `PersistentChunkStore` non e' stato toccato (nessun file di CACHE-01
   modificato).
3. Il budget dichiarato e' applicato dallo store (eviction + `quota-exceeded`)
   in aggiunta alla quota reale del browser, come chiede C-CACHE ("budget ed
   eviction dichiarati"); senza budget esplicito vale 32 MiB.
4. Un database di versione superiore a quella del client e' trattato come
   storage indisponibile (niente lettura di entry con schema ignoto).
5. La chiave include `schemaVersion` e `compilerVersion` nel record
   denormalizzato per permettere la scansione con una sola richiesta: e' un
   dettaglio interno, la chiave primaria resta l'id del contratto.
6. I test unitari non usano `fake-indexeddb` (non aggiungibile come dipendenza):
   il fake minimale sta nel file di test, come da istruzione operativa.
7. AC2 e AC3 restano aperti perche' dipendono dal gate E2E, non eseguibile qui.
